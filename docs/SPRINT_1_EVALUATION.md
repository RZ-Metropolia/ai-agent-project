## How we checked correctness

- **Tool choice:** The tool trace shows which tools the agent called. We compare it with the expected tools for each scenario.
- **Arguments:** The executor validates every argument with the Pydantic schema. We check the trace for the correct labels, allergens, items, and budget.
- **Grounded facts:** We compare prices, ingredients, allergens, and stock in the answer with a direct SQL query and with the API response.
- **Draft check:** We read the stored draft back from SQLite. Its subtotal must equal the sum of the database prices, and every item must pass the requested rules.
- **Safe handling:** In failure scenarios, no new draft row may exist, and the answer must state the reason.
- **Runner:** `python -m src.evaluation --mode groq --runs 2` (or the Colab notebook) runs the scenarios and does these checks automatically. The checks for each scenario are in `src/evaluation.py`, and each check is marked critical or non-critical. The answer checks only look for key words, so a person reads each answer before recording the result. The answers, checks, and tool traces are saved in `docs/eval_results/`.
- **Retries:** Groq refuses a tool call with a misspelled tool name (HTTP 400 `tool_use_failed`). The loop then asks the model again, up to 2 times. The result files record the number of retries as `model_retries`.
- **Local runs:** local mode uses greedy decoding (no sampling), so it gives the same output each time. One run per scenario is enough there.

**Result rule:**

- **Pass:** All checks pass: correct tools, correct facts, and a correct draft or a correct refusal.
- **Partial:** Only a non-critical check fails. Example: the result is safe, but the answer does not state the total, or it mentions a non-matching item as an option.
- **Fail:** A critical check fails. Examples: invented data, an unsafe or missing draft, a draft created when it must be refused, or a missing key fact.

## Short evaluation summary

- **Scenarios completed:** Groq: 16 scenario runs (8 scenarios × 2 runs); **passed:** 12; **partial/failed:** 2 partial, 2 failed. Local Qwen: 8 scenarios (2 runs with identical results); **passed:** 6; **partial/failed:** 2 partial, 0 failed.
- **What worked reliably:** The safety rules held in every run of both modes. No draft was saved when the request had to be refused (E-04 to E-08). Each saved E-01 draft passed every rule: vegetarian, in stock, pickup 18:30, and a subtotal of 16.00 € that equals the database prices. Every price, allergen, and stock value in the answers came from a tool result. During the inventory outage (E-06), every run refused with a clear reason and gave no stock value.
- **Most important failure or limitation:** Groq refused 2 of the 16 scenario runs before our executor saw the tool call: E-01 run 1 had a broken call format, and E-07 run 2 had a misspelled tool name. Both scenarios stopped without an answer. The retry did not help: it sends the same prompt at temperature 0, and all 3 tries returned the same broken call (`model_retries: 2`). The local 4B model made no broken tool calls with the same tools, so the likely cause is how Groq serves this model or checks tool calls. We did not verify this.
- **What we would change or test next:** When Groq refuses a tool call, retry with a short note that names the correct tools. The note changes the prompt, so the model does not repeat the same output. Then run E-01 and E-07 again. We would also decide whether the E-05 answer must name Berry Sorbet, or whether a correct "no match" answer is enough.

## What we cannot conclude

- The menu and stock data are synthetic. The results do not prove real allergy safety.
- Eight scenarios with two runs each do not prove general reliability for other requests.
- The results are valid only for the model versions listed in the test setup.
